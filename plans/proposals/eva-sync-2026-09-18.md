## 〇、关键结论(先看这段)

1. **EVA 不需要新的"实体类型"——它就是 craft**。JNO 里出舱 = `CraftSplitter` 分裂出**一个新的独立 `CraftNode`**,回舱 = `CraftSplitter.MergeCraftNode` 合并回去。所以同步 EVA **本质上就是同步 craft 集合**,与 [`multi-craft-sync-2026-08-16.md`](multi-craft-sync-2026-08-16.md) 是同一个问题,不需要另起炉灶。
2. **但"只做 EVA 不做多 craft"是一条死路**。理由见 §二:**没有任何事件能告诉你"这次分裂是 EVA"**——分裂出来的就是普通的新 craft,`ProcessDisconnectedBody` 是分离器、抛掷物、EVA 三者共用的唯一通道。要么做 craft 集合同步(通用),要么写一个必然覆盖不全的特例分支。
3. **现状:一按 EVA 就崩,而且是"错位"而不是"消失"**。玩家出舱后 `FlightSceneScript.Instance.CraftNode` 变成 EVA 节点,而 mod 的 `LocalNodeId` 只在 1.5s 重发循环里刷新 → 中间这段时间**状态包用旧 NodeId 装着 EVA 节点的坐标**,接收端把"对方飞船幽灵"瞬移到 EVA 所在处(§三)。
4. **真正的新难点不是位置,是"乘组成员(CrewMember)"这份游戏级全局状态**(§四)。`EvaData.CrewId` 是存档内自增 id,接收端按它去**本地** `gameState.Crew.GetCrewMember(id)` 取人(`EvaData.cs:295`);两台机器的 roster 天然不一致 → 幽灵 EVA 大概率显示「Unassigned」甚至引用到本地某个真实乘员。这一条**现有 plan 完全没覆盖**,是 EVA 相对"普通残骸船"唯一的额外工作量。
5. **建议路线:先做多 craft 身份层(MC1),EVA 作为它的第一个消费场景上线**(§八 M0~M3);动画/舱内姿态这类"表现层"可以后置,别一开始就追求像。
6. **顺手发现的两处协议缺口**(不只影响 EVA,但 EVA 会把它们暴露得很明显):① 状态包**没有 craft 身份**→ 收包端无从路由(§三);② `CraftControls` 里 EVA 用的是**专有字段** `EvaMoveFwdAft / EvaMoveUpDown / EvaStrafe / EvaTurn / …`,现有 `ControlVisualSync` 一个都没写(`ControlVisualSync.cs:41-52`)→ 远端背包喷焰/动画分支必然不对(§4.3)。
7. **参考 Luna 的正确姿势**:Luna 的 EVA 是"**一个新 Vessel** + 独立 Guid + 复用 Vessel 位置通道 + 回舱时 `SendVesselRemove(evaId)` + 重发母船 proto"(`VesselCrewEvents.cs:16-41`)。**对照组身、通道复用**,不要为 EVA 单独发明一套消息。但**"乘员是谁"这层两边模型不同**(KSP 的 kerbal 是独立实体,JNO 的乘员是存档级 roster + 部件引用),不能照抄。

## 一、EVA 机制事实(反编译确认)

### 1.1 结构:Drood 是"带 `EvaScript` 的 CommandPod 部件",出舱后才成为独立 craft

| 事实 | 证据 |
|---|---|
| `CommandPodScript.IsEva = (EvaScript != null)`,EVA 部件同时是**命令舱** | `CommandPodScript.cs:132,142,476-477` |
| `EvaData` 挂在部件上,`CrewId` / `CrewName` 随 craft XML 序列化 | `EvaData.cs:24,29,77-101` |
| `EvaActive = (CrewCompartment == null && !刚回舱成功过)` —— **在舱里就不算 EVA** | `EvaScript.cs:440-445` |
| 出舱 = 销毁物理关节 → body 脱离 → 分裂成新 `CraftNode` | `EvaScript.cs:2259-2303`(`UnloadFromCrewCompartment` 内 `bodyJoint.Destroy()`);`CraftSplitter.cs:82-108`(`ProcessDisconnectedBody`) |
| EVA body 必然够格成节点:单部件的 Drood 会命中"包围盒任轴 > 10m"或 `PreventDebris` | `CraftSplitter.cs:216-250`(`DetermineCraftNodeEligibility`) |
| 新节点创建 + `CraftNodeAdded` 事件 | `CraftSplitter.cs:111-130`(`SplitCraftNode` → `FlightState.AddCraft(craftNode2, craftNode)`);`CraftNode.cs` / `FlightState.cs` 同 §一 multi-craft plan |
| 出舱后 `CrewMember.NodeId` 被改写为新节点 id | `EvaScript.cs:2037-2044`(`OnMovedToNewCraft` ← 由 `CraftSplitter.cs:128` 的 `OnMovedToNewCraft` 触发) |

### 1.2 出舱调用链(顺序即协议语义)

```
玩家点 EVA(部件菜单 / 乘组面板)
  → CrewCompartmentScript.UnloadCrewMember(crew, takeControl=true)
      ├─ crew.TakeControl()                                   CrewCompartmentScript.cs:361-375
      │    ├─ if (!EvaActive) UnloadFromCrewCompartment()      EvaScript.cs:1267-1280
      │    │     └─ bodyJoint.Destroy() → body 脱离             EvaScript.cs:2259-2303
      │    │        └─ CraftSplitter.ProcessDisconnectedBody → SplitCraftNode → AddCraft ★CraftNodeAdded
      │    └─ SwitchToCommandPod()                             EvaScript.cs:2249-2256
      │         └─ FlightSceneScript.ChangePlayersActiveCommandPodImmediate(pod, evaNode, ignoreDistance:false)
      │              └─ SetCraftNode(evaNode) → 旧船 SetIsPlayer(false) / 新 EVA SetIsPlayer(true)
      │                   └─ FlightSceneScript.CraftChanged 事件   FlightSceneScript.cs:1539-1581
      └─ CrewExit 事件
```

**要点(容易踩)**:

- **分裂发生在切换控制权之前**。`TakeControl()` 先 `UnloadFromCrewCompartment`(→ 分裂)再 `SwitchToCommandPod`。所以"看到 `CraftNodeAdded` 时玩家还没接管"是正常时序,别指望"新节点出现 = 玩家已 EVA"。
- **切换控制权有距离校验**:`ChangePlayersActiveCommandPodImmediate(..., ignoreDistance:false)` → 距离超 `PhysicsDistance*1000-100` 会**返回 false 而失败**(`FlightSceneScript.cs:361-387`)。极端情况下节点分裂了但玩家没接管成功(旧船仍是活动船)。
- **切换成功会把 `AllowPlayerControl = true` 写死在目标节点上**(`FlightSceneScript.cs:383`)。这正是 multi-craft plan §8.1-3 要拦该方法的原因,对 EVA 同样成立(§七)。
- **可观测事件**:出舱只能靠 `CraftNodeAdded`;另有 `FlightSceneScript.CraftChanged`(**只在本机活动节点变化时触发**,`FlightSceneScript.cs:1561-1565`),这是"我 EVA 了 / 我回舱了 / 我换船了"的**本地权威信号**,也是最省事的重采样触发点。

### 1.3 回舱调用链

```
LoadIntoCrewCompartment(compartment, onCompleted, announceBoarding)
  EvaScript.cs:947-964
  └─ [下一帧 ExecuteYield<WaitForEndOfFrame>] LoadIntoCompartment()   EvaScript.cs:758-865
       ├─ 找 compartment 上的 Surface / Eva 类型 AttachPoint                      :789-796
       ├─ ChangePlayersActiveCommandPodImmediate(舱的 pod, 母船节点)  ★先切回母船   :800
       ├─ 同步刚体速度/角速度 + 摆到舱位                                            :807-810
       └─ UpdateNodeName(ConnectParts(舱, attachPoint, Drood, EvaAttachPoint).CraftNode, 原名)
            └─ ConnectParts → CraftSplitter.MergeCraftNode(EVA节点 → 母船节点)      :812 / 1376-1411
                 └─ 母船吸收 EVA 节点 → sourceCraftNode.DestroyCraft() ★CraftNodeRemoved
                                                                  CraftSplitter.cs:22-79
```

**要点**:

- **回舱 = `MergeCraftNode`,和对接(docking)完全同一条路径**(`DockingPortScript.cs:552` 也调它)。所以 multi-craft plan §8.1-4 的结论"对接 = 被吸收方走 `CraftNodeRemoved` + 重发 dominant XML,**无需显式 CraftMerge 消息**"**可以直接复用到 EVA 回舱**——这是本方案最大的一处"白捡"。
- **dominat 判定不同**:对接是"`IsPlayer` 优先"(`DockingPortScript`,见 multi-craft plan §8.1-4);回舱是**调用方写死的**——`ConnectParts` 里先看 `partB.CraftNode.IsPlayer` 再决定谁吸收谁(`EvaScript.cs:1376-1394`),即**玩家所在的 EVA 节点被母船吸收**。
- **回舱不是原子的**:整段包在 `WaitForEndOfFrame` 里,期间 EVA 节点仍然存在。远端可能在这中间收到若干 EVA 状态包 → 协议必须允许"craft 即将消失"的竞态(§五 R4)。
- **EVA 节点被 `DestroyCraft` 后,`CraftNodeRemoved` 才在下一帧触发**(游戏 `ProcessDestroyedCraftNodes`),与现有 `RemoveRemoteCraft` 的经验一致。

## 二、为什么"单独给 EVA 开小灶"会失败

一个自然的想法是:"就让它支持**每玩家两艘**——主船 + EVA"。这条路有三个硬伤:

1. **没有办法判定"这次分裂是 EVA"**。分裂统一走 `CraftSplitter.ProcessDisconnectedBody`(`CraftSplitter.cs:82`),分离器抛掉的一级、抛掷物、EVA 走的是**同一个函数**;`ProcessDisconnectedBody` 之后才 `DetermineCraftNodeEligibility` 决定是"新节点"还是"craft 内 debris"(`CraftSplitter.cs:87-106`)。想特判就得在 `CraftNodeAdded` 回调里反查"新节点里是不是有 `EvaData`"——**那已经是通用 craft 识别了,不如直接做通用**。
2. **"两艘"这个上限是假的**。出舱后玩家还可能:从 EVA 抛掷物、从 EVA 分离、再出第二个乘员、抛下旧船开 EVA 飞走、和别人的船对接。这些都会产生"同一玩家名下的第 3、第 4 个节点"。写死 `主船 + EVA` 只会把同一个 bug 推到下一个场景。
3. **回舱会让"主船"这个概念翻转**。回舱后 EVA 节点消失、母船吸收它,**玩家名下的节点数又回到 1**,但此时**母船 XML 已经变了**(多了一个 Drood body + 乘组变化)→ 必须走"结构变化 → 重发 XML"这条通用路径,否则远端母船永远少一个乘员。

**结论**:EVA 是"多 craft"的**第一个杀手级用例**,不是它的替代品。正确顺序是先有身份层与生命周期(MC1),EVA 顺手就有。**这也是把 EVA 排在多 craft 里的理由,而不是反过来。**

## 四、EVA 独有的两个"非位置"难题(现有 plan 未覆盖)

### 4.1 乘组成员(CrewMember)是本机全局状态,不随包走

- `EvaData._crewId` 随 craft XML 序列化(`EvaData.cs:24,77-81`),但**初始化时是拿这个 id 去本地 roster 查人**:
  `this.CrewMember = gameState.Crew.GetCrewMember(this._crewId);` —— `EvaData.cs:291-296`
- `CrewManager` 是**存档级全局单例列表**,id 是存档内自增(`CrewManager.cs:20,61-71`),`CrewMember` 带 `Id / NodeId / Location / Name / State`(`CrewMember.cs:34-54`)并持久化进存档(`CrewMember.cs:62-70`)。
- 因此接收端 spawn 幽灵 EVA 时:
  - 若本地 roster 里**没有**该 `crewId` → `CrewMember == null` → 显示「Unassigned」,`EvaScript` 多处 `Data.CrewMember != null` 判空会跳过(`:2039`、`:2422`)→ 名字/状态不对但一般不崩;
  - 若本地**恰有**同 id 的成员(两人各自开新档,roster 都从 id=1 开始)→ 幽灵 EVA **引用了本地那个真实乘员**;若该成员同时被本地船占用,就是"一个人同时在两条船上"的语义污染,**且 `CrewMember.NodeId` / `State` 会被幽灵改写**。
- **`CrewMember.NodeId` 是"本机节点 id"且会持久化**(`CrewMember.cs:39,66`;`CrewManager.cs:35-43` 加载时清理失效 id)。远端的节点 id 在本机毫无意义,**绝不能让幽灵 EVA 的 `OnMovedToNewCraft` 往本地真实乘员身上写**。

**可选方案**:

| 方案 | 做法 | 代价 |
|---|---|---|
| **C1(建议)** | 房主把每个玩家的**乘组名单**(`crewId + name`)作为一次性 roster 元数据下发;接收端为对端乘员在**本地 roster 里建"影子成员"**(保留对端 id/名字,`State` 标记为影子、不参与 `GetAvailableCrew`),并把幽灵 EVA 的 `EvaData.CrewMember` 指过去 | 需要改 `CrewManager` 行为或加一层映射表;`GetAvailableCrew`(`CrewManager.cs:86-103`)要排除影子成员 |
| C2 | 不动 roster,只在幽灵上写 `EvaData.AssignCrewMember(影子/本地占位)` 并把名字放进 craft 名 | 最省事,但舱内乘组面板查看对端船时乘员名会不对/重复 |
| C3 | 全量同步 roster(加删除/改名) | **不做**:roster 是存档级持久状态,同步它等于同步存档,超出 MVP |

> **MVP 建议**:先做 C2(名字对即可),把 C1 列为 M4 打磨项。**但无论选哪个,都必须阻断"幽灵写本地 `CrewMember.NodeId`/`State`"这条路径**(§七 P3)。

### 4.2 幽灵 EVA 的本地模拟必须显式关掉

`EvaScript` 是 `PartModifierScript` 且实现 `IFlightUpdate / IFlightFixedUpdate / IFlightLateUpdate`(`EvaScript.cs:45`),**幽灵船同样会收到这些回调**(与引擎 modifier 同理,见 `JetEngineGhostPatch.cs` 头注释)。逐条核对结果:

| 回调内行为 | 是否会打坏幽灵 | 证据 |
|---|---|---|
| 输入驱动力 / 喷气背包 | **否**:`if (IsPlayerCraft) UpdateMovement(...)`;`IsPlayerCraft` = "本机活动节点是不是我"(`:447`),幽灵恒 false | `EvaScript.cs:871-874` |
| 每帧改 `rigidBody.interpolation` | **是(轻)**:非本机船走 `GetShouldInterpolate` 的另一分支,可能把幽灵刚体设成 `Interpolate`,与 mod 的每帧直接写 transform 打架 | `EvaScript.cs:849`、`:1566-1587` |
| 站立自动回正 / 运动学转向 | **潜在**:`!ShouldInterpolate` 时会走 `UpdateKinematicTurning()` / `UprightCharacter()` | `EvaScript.cs:875-885` |
| 摄像机乘员视角注册 | **否**:有 `IsPlayerCraft` 守卫 | `EvaScript.cs:2429-2445` |
| 被当作引擎 / 燃料消费者处理 | **否(已核实)**:`EngineVisualSync` 的采样与建表都按 `mod is JetEngineScript / RocketEngineScript / EngineScript` 三类白名单匹配(`EngineVisualSync.cs:185,191,240,276,316`),`EvaScript` 不在其中 | `EvaScript.cs:45`;`EngineVisualSync.cs:169-201,214-337` |

**结论**:不能只靠"物理关掉"——需要一条与 `JetEngineGhostPatch` 同构的 **`EvaGhostPatch`**(幽灵 EVA 跳过 `FlightFixedUpdate`)或用 `MpNetworkManager.IsRemoteCraftNode` 守卫,把 `interpolation` / 回正 / 转向这三处按住。**这不影响出舱触发,只在接收端生效,风险低。**

### 4.3 EVA 有一套**独立的控制通道**,现有协议一个字段都没传

`CraftControls` 里 EVA 用的是**专有字段**,与飞船的 `Translate*`(RCS 平移)不是同一组(`ModApi/Craft/CraftControls.cs:97-207`):

| 字段 | 作用 | 现状 |
|---|---|---|
| `EvaMoveFwdAft` / `EvaStrafe` / `EvaMoveUpDown` | 喷气背包 / 行走三轴输入 | ❌ **未传** |
| `EvaTurn` / `EvaPitch` / `EvaRoll` | 角色朝向与姿态输入 | ❌ **未传** |
| `EvaWalk` / `EvaAnalogJump` / `EvaJumpPowerScalar` | 行走 / 跳跃 | ❌ **未传** |
| `EvaShootTether` / `EvaTetherLength` / `EvaTetherLengthOffset` | 抓钩 / 系绳 | ❌ **未传** |

接收端 `ControlVisualSync.ApplyRemoteControls` 只写 `Pitch/Yaw/Roll/Brake/Throttle/Slider1-4/TranslateForward|Right|Up`(`ControlVisualSync.cs:41-52`),**没有任何 `Eva*` 字段**。

**影响分级**:

- **位置/朝向本身不受影响**——远端 EVA 的位姿来自状态包,不靠本地重演输入(同理现有飞船)。
- **受影响的是"读取控制输入的本地表现"**:喷气背包粒子/背包火焰、角色行走/空中动画分支、抓钩与系绳的可视化。
- 其中**抓钩/系绳是"实体行为"而非纯视觉**(`GrapplingHook` 会把 EVA 与目标刚体连起来),MVP 建议**明确不支持**(与"无双向碰撞物理"同级列入已知限制),而不是半吊子同步。
- **MVP 结论**:先把 `EvaMoveFwdAft / EvaMoveUpDown / EvaStrafe / EvaTurn` 四个**输入标量**加进状态包尾部(与现有 `Translate*` 同级,各自 1 个 float),用于驱动远端背包火焰与动画分支;`EvaWalk`/跳跃/抓钩后置。

## 五、协议设计建议

### 5.1 身份(前置:MC1 必做)

沿用 multi-craft plan §四:**mod 自造 `Guid`**,本地 `Dictionary<int /*nodeId*/, Guid>` 映射 + 状态包带 `(ownerId, craftGuid)`。EVA 只需要新增**一个标量标注**:

```
CraftInfo { Guid craftGuid; int ownerId; string xmlHash; CraftKind kind; }
CraftKind = Normal | Eva | Debris
```

- `kind` **由接收端可自行判定**(XML 里有没有 `EvaData`),所以它**不必进协议**——建议本地算,省字段与版本兼容成本。
- `EvaMode` 也**不必进协议**:`EvaActive`(在舱 / 出舱)在幽灵生成时由 XML 结构天然决定(出舱时 EVA 部件单独成节点)。**只有"舱内可见乘员"这种同 craft 内的表现才需要额外字段**(§5.3)。

### 5.2 状态包(增量,尾部追加,沿用现有 EOF 容错约定)

| 字段 | 必要性 | 说明 |
|---|---|---|
| `CraftGuid` | **必须** | 替换/补充 `nodeId` 作为路由键;`nodeId` 降级为本地调试信息 |
| `CraftSituation`(Ground/Orbit) | **建议** | 现有实现写死"表面锁定 + `InContactWithPlanet=true`"(`MpNetworkManager.cs:2084`、`:1693`);**轨道上出舱**的 EVA/母船沿用这条会掉进地里。multi-craft plan MC2 已列为待办 |
| `EvaMode`(Eva / EvaInChair) | 可选 | 目前只有 `EvaChairScript`/`EvaInChair` 变体用到(`EvaScript.cs:450-460`);MVP 可省略 |
| `EvaAnimState`(Idle/Walk/Airborne/Jetpack) | 可选(表现层) | 用于驱动远端角色动画;MVP 可用"`Situation` + 速度"粗略推导,先不传 |
| `EvaMoveFwdAft` / `EvaMoveUpDown` / `EvaStrafe` / `EvaTurn` | **建议(MVP 内)** | EVA 专有输入,见 §4.3;各 1 float,合计 +16B/包,可忽略 |

> **不要新开消息类型**。出舱 = 新的 `CraftInfo`(走现有按需 XML 下载);回舱 = 被吸收方的 `CraftRemove`,**复用现有 `CraftNodeRemoved` → `RemoveRemoteCraft`(DestroyCraft)链路**(`MpNetworkManager.cs:1749-1803`)。

### 5.3 生命周期钩子(最小改动集)

| 场景 | 钩子 | 动作 |
|---|---|---|
| 出舱 / 分离 / 任何新节点 | `FlightState.CraftNodeAdded` | 分配 `Guid` → 广播 `CraftInfo`(新 craft 的 XML 由对端按需下载) |
| 回舱 / 对接 / 销毁 | `FlightState.CraftNodeRemoved` **或** `CraftNode.Destroyed` | 广播 `CraftRemove(guid)` |
| **本机换节点(我 EVA 了 / 我回舱了 / 我换船了)** | `FlightSceneScript.CraftChanged`(`FlightSceneScript.cs:1561-1565`) | **立即** `RefreshLocalCraft()` + 立即发一包(不等 1.5s 循环)——**这一条是治 §三 错位链的关键** |
| 结构变化(母船吸回 EVA 后 XML 变了) | 现有 `RefreshLocalCraft` 的 `craftXml` 比较(`:359`) | 已可用,但要保证"重发 XML"能触发对端**重建**该幽灵(当前 `_remoteCrafts` 命中即 return,`§三` 最后一行为空) |
| 断线 / 踢出 | 现有 `HandlePlayerLeft`(`:1652`) | 改为**删除该玩家名下所有 craft**,而非单个 |

### 5.4 频率分级(EVA 天然属于"活动船")

- 玩家**正在驾驶**的节点(EVA 或飞船)= 活动船,全速(现有 20Hz)。
- **被抛弃的母船**(玩家 EVA 飞走后留在原地)= 次要节点,降到 1~5Hz。
- 判定依据:**房主/owner 侧的 `FlightSceneScript.CraftNode` 就是活动节点**,其余都算次要——不需要额外协议,owner 自己在采样时决定发哪个频率即可(把频率档位写进包或按节点分开发送定时器)。

## 六、与 LunaMultiplayer 的对照(可抄什么 / 不可抄什么)

Luna 的 EVA 处理集中在 `LmpClient\Systems\VesselCrewSys\VesselCrewEvents.cs` 与 `LmpClient\Events\EvaEvent.cs`:

| Luna 做法 | 代码 | 对 JNO 的启示 |
|---|---|---|
| EVA 出舱 = **一个新的 Vessel**,走**通用 Vessel proto 广播** | `VesselCrewEvents.CrewEvaReady` → `SendVesselMessage(evaVessel, true, "Kerbal EVA")`(`:38-41`) | ✅ **同构**:JNO 出舱也是新 craft,直接复用通用 craft 广播,不要专线 |
| 回舱 = 删掉 EVA 那艘船 + 重发母船 | `OnCrewBoard`:先 `SendVesselRemove(kerbalId)` → `ReleaseAllVesselLocks` → `KillVessel` → **再** `SendVesselMessage(vessel,…)`(`:16-25`) | ✅ **同构且更简单**:JNO 的 `MergeCraftNode` 会自己 `DestroyCraft` 被吸收节点(`CraftSplitter.cs:75`)→ 直接复用 `CraftNodeRemoved`,连 `CraftRemove` 都不必显式发 |
| EVA 实体有**独立 Guid**,位置更新走通用 Vessel 位置通道 | `EvaReady.cs:9-24` + VesselPosition 系统 | ✅ 印证"EVA 不是特例通道";JNO 侧就是 §5.2 的 `CraftGuid` |
| 回舱/上座时**释放该 kerbal 的锁** | `:21` | ⚠️ JNO **无锁系统**(self-authoritative,MVP 不需要);但"回舱后谁拥有该实体"的语义在 JNO 里由"节点是否还存在"天然表达,不需要锁 |
| KSP 里 kerbal 是**独立于 vessel 的 roster 实体**,Luna 还需同步 `KerbalInfo` | `LmpCommon\Message\Data\Kerbal\KerbalInfo.cs` 等 | ⚠️ **不可直接抄**:JNO 的乘员是**存档级 roster + 部件引用**(§4.1),KSP 是"kerbal 对象挂到 part 上"。JNO 侧对应物是"影子乘员"映射(§4.1 C1/C2) |
| EVA 相关 Harmony 补丁(上座/离座/boarding) | `LmpClient\Harmony\KerbalEVA_*.cs`、`KerbalRoster_SackAvailable.cs` | ⚠️ JNO 侧对应的是**换节点总入口** `ChangePlayersActiveCommandPodImmediate` 的拦截(§七),不是上座那一步 |

> **一句话**:Luna 的**结构与通道**可以照抄(新实体 + 通用通道 + 回舱删实体重发母体),但**"乘员是谁"这层**两边模型不同,JNO 必须自己解决(§4.1)。

## 十、方法论备注(本次研究踩到的坑)

- **`<JNO_CODE>` 的反编译源缺 local function 类**。`EvaScript.cs` 里 `LoadIntoCrewCompartment` 的内嵌 `<>c__DisplayClass209_0` / `g__LoadIntoCompartment|0` **在源码树里不存在**(只有一行调用,`EvaScript.cs:949-962`),导致**回舱的真实实现读不到**(而它正是"回舱 = `MergeCraftNode`"的关键证据)。
- **解法**:用 `ilspycmd`(已在 `~\.dotnet\tools`)直接反编译安装目录的 `SimpleRockets2.dll`:
  `ilspycmd "<SR2_GAME>\SimpleRockets2_Data\Managed\SimpleRockets2.dll" -t Assets.Scripts.Craft.Parts.Modifiers.Eva.EvaScript`
  输出为 **UTF-16**,需转 UTF-8 后再读。**后续遇到"源码里只有调用没有实现"的成员,一律按此法取 IL 级实现**。
- **两侧对照的可靠性**:未在 `EvaScript.cs` 里出现的成员(如 `TakeControl` 的真实分支)以 **DLL 反编译**为准;源码树版本会给出相同的行内注释与 `Token` 行,便于交叉定位。
